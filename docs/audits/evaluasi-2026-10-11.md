# Evaluasi Nuctech Warehouse — 11 Oktober 2026

## Status perbaikan — 12 Oktober 2026

Temuan di bawah merupakan baseline audit sebelum perbaikan. Perbaikan sudah diimplementasikan dan tes reproduksi diganti dengan `tests/Feature/AuditRegressionTest.php`, yang mengharapkan perilaku aman. Hasil verifikasi terakhir: 64 tes backend lolos (558 assertions). Lihat README untuk migrasi relasi site laporan dan kebutuhan queue worker. Migrasi relasi laporan sudah diterapkan pada MySQL lokal (environment local, host loopback). Database produksi belum disentuh.

## Kesimpulan audit awal

Belum layak dinyatakan siap produksi tanpa perbaikan akses lintas site, integritas persetujuan reimbursement, dan penghapusan data payroll. Build berhasil, tetapi ada bug fungsional dan keamanan yang dapat direproduksi. Evaluasi ini tidak mengubah kode aplikasi atau empat file yang sudah memiliki perubahan lokal.

## Cakupan dan batas pemeriksaan

Pemeriksaan source routes, middleware, controller, layanan akses, model, migrasi, import/export, frontend dan tes. Fokus mendalam pada autentikasi/sesi, inventaris dan transfer, laporan, reimbursement termasuk perubahan bulk terbaru, jadwal/absensi, karyawan, cuti dan payroll. Telegram ditinjau dari source dan tes dengan HTTP fake; tidak ada pesan atau backup dikirim.

Tes memakai SQLite in-memory dan storage palsu. Belum memverifikasi browser secara visual, deployment produksi, data MySQL aktual, concurrency MySQL, PDF kompleks/Ghostscript, pemulihan backup, performa beban besar, ataupun advisori kerentanan dependency terkini. Tidak ada klaim bahwa seluruh kemungkinan masalah telah ditemukan.

## Temuan terkonfirmasi

P1 = prioritas tinggi, risiko akses/data/persetujuan; P2 = kerusakan fungsi atau data yang perlu diperbaiki.

### 1. P1 — Fast approve melewati otorisasi site dan tahap persetujuan

Lokasi: `app/Http/Controllers/AdminReimbursementController.php:1367`.

`fastApprove()` hanya mengecek nama role. Tidak memanggil ReimbursementAccess, tidak membatasi pemilik/site, dan tidak memeriksa status saat ini. Tes membuktikan team leader site B dapat mengubah klaim pending milik site A menjadi approved. Status rejected juga tidak dilindungi oleh pengecekan tahap di metode ini.

Perbaikan: tetapkan hak fast-track secara eksplisit, gunakan policy yang sama dengan approval biasa dan transaksi dengan row lock; validasi transisi status dan audit pelakunya.

### 2. P1 — Edit klaim mempertahankan persetujuan lama

Lokasi: `app/Http/Controllers/AdminReimbursementController.php:1267`.

Pemilik boleh mengedit klaim pending_station/pending_manager. Nominal, rincian dan lampiran berubah tanpa mengulang alur approval atau menghapus tanda tangan lama. Tes mengubah nominal 100 menjadi 9.000.000 pada pending_manager; status dan tanda tangan leader tetap dipertahankan.

Perbaikan: kunci perubahan isi setelah persetujuan pertama, atau buat revisi yang membatalkan persetujuan terdahulu dan kembali ke tahap awal. Gunakan row lock untuk menghindari benturan edit/approve.

### 3. P1 — Team leader dapat mengubah master site lain

Lokasi: `routes/web.php:52`, `app/Http/Controllers/SiteController.php:59` dan `:79`.

Resource sites/site terbuka untuk team_leader, sedangkan update/destroy tidak memeriksa kepemilikan site. Tes membuktikan team leader site B dapat mengganti nama site A. Penghapusan site juga berisiko menghapus data yang memiliki foreign key cascade, termasuk stok.

Perbaikan: batasi pengelolaan master site ke role yang memang berwenang atau terapkan policy site secara konsisten sebelum mutasi.

### 4. P1 — Ekspor jadwal dan perubahan pola tidak dibatasi site

Lokasi: `app/Http/Controllers/ScheduleController.php:467` dan `:497`.

Export hanya mengganti parameter `all` menjadi site pengguna; ID site lain yang eksplisit tetap diterima. updateSitePattern langsung menulis ke site dari URL. Tes membuktikan team leader bisa mengunduh jadwal dan mengubah pola site lain. updateSingle juga melewati pemeriksaan beda site jika pengguna tidak memiliki site_id.

Perbaikan: gunakan SiteAccess untuk seluruh endpoint, termasuk aturan kelompok mesin jika memang dibutuhkan; tolak akun tanpa penugasan site secara default.

### 5. P1 — API absensi mengirim data sensitif karyawan

Lokasi: `app/Http/Controllers/AttendanceController.php:96`, khususnya respons Employee collection; `app/Models/Employee.php`.

Endpoint yang dapat dipakai employee_role mengembalikan model lengkap. Tes memastikan NIK dan nomor rekening karyawan satu site ada di JSON; basic_salary juga merupakan atribut model yang tidak disembunyikan. Tampilan absensi tidak memerlukan seluruh atribut personal/payroll tersebut.

Perbaikan: gunakan resource/DTO dengan allowlist atribut absensi. Jangan mengandalkan elemen UI yang tidak menampilkan field sensitif.

### 6. P1 — Bulk force delete dapat menghilangkan lampiran walaupun transaksi dibatalkan

Lokasi: `app/Http/Controllers/AdminReimbursementController.php:1477`.

Loop mengotorisasi dan menghapus file satu per satu. Ketika ID berikutnya tidak berwenang, database rollback tetapi file yang sudah dihapus tidak kembali. Tes dengan satu klaim sendiri lalu satu klaim orang lain menghasilkan 403, record pertama masih ada, lampirannya hilang.

Perbaikan: otorisasi seluruh pilihan sebelum side effect, lock record selama mutasi, dan lakukan penghapusan file setelah commit dengan mekanisme retry/cleanup yang jelas.

### 7. P1 — Generate ulang payroll historis menghapus gaji mantan karyawan

Lokasi: `app/Http/Controllers/SalaryController.php:460`.

Cleanup memakai status/is_active saat ini, tanpa membandingkan resign_date dengan periode payroll. Tes: karyawan resign 30 September, gaji Agustus sudah ada; generate Agustus menghapus record gajinya. Query karyawan aktif selanjutnya tidak memasukkannya kembali.

Perbaikan: tentukan eligibility berdasarkan periode join/resign, simpan periode payroll eksplisit, dan hindari penghapusan histori karena perubahan status terkini.

### 8. P2 — Route create/export laporan tertangkap sebagai slug

Lokasi: `routes/web.php:76`.

`/{slug?}` didaftarkan sebelum `/create` dan `/export`. Kedua URL dianggap slug site, kemudian 404. Dibuktikan dengan tes HTTP dan kegagalan tes export bawaan.

Perbaikan: daftarkan route statis terlebih dahulu atau pisahkan namespace URL site.

### 9. P2 — Laporan tersimpan tetapi tidak muncul pada daftar site

Lokasi: `app/Http/Controllers/ReportController.php:46` dan `:127`.

Store memvalidasi dan menyimpan site_machine sebagai slug, tetapi index mencarinya menggunakan machine_name. Tes POST berhasil dan record ada, tetapi paginator site menghasilkan nol laporan.

Perbaikan: gunakan site_id sebagai foreign key; migrasikan nilai lama secara terkontrol. Penggunaan slug juga rapuh karena SiteController membuat slug baru pada setiap update site.

### 10. P2 — Import nominal berformat Indonesia menghasilkan angka salah

Lokasi: `app/Imports/ReimbursementImport.php:63`.

Input teks `1.000.000` diproses dengan floatval dan menjadi `1`. Tes mengonfirmasi nilai tersimpan 1.00. Cell Excel numerik asli tidak terkena contoh ini; masalah muncul pada cell teks dengan pemisah ribuan.

Perbaikan: pisahkan parsing cell numerik dan string, tetapkan format desimal/ribuan yang didukung, dan tolak format ambigu dengan nomor baris kesalahan.

## Temuan tambahan dari source yang belum diuji khusus

- `ReportController::search()` memakai Report::query tanpa pembatas site. `ReportExport` mengambil seluruh laporan; ketika route export diperbaiki, tambahkan scope akses sebelum membuka kembali fitur tersebut.
- `ScheduleController::clear()` mengganti site yang diminta dengan site pengguna tanpa menolak mismatch. Request yang menyebut site B dapat justru menghapus jadwal site A milik pengguna. Ini menjelaskan kegagalan tes 403 versus 302; bukan bukti bahwa endpoint tersebut menghapus site B.
- View composer `AppServiceProvider.php:57` menimpa counter dashboard yang sudah dihitung controller dengan cache global, termasuk mengganti total qty sparepart menjadi jumlah master sparepart. Angka dan scope dashboard tidak konsisten.
- Recycle bin reimbursement memberi manager daftar semua klaim, tetapi manage() hanya mengizinkan klaim sendiri kecuali superadmin/administration. Sebaliknya administration hanya melihat trash sendiri. Daftar dan aksi perlu memakai policy yang selaras.
- SalaryController menghitung data periode lama menggunakan record Salary terbaru tanpa batas periode, dan beberapa perhitungan menggunakan jadwal, bukan absensi aktual. Butuh spesifikasi payroll dan tes sebelum hasilnya dijadikan dasar pembayaran.
- Holiday service menyimpan respons gagal sebagai array kosong selama satu hari; jadwal/rekap yang bergantung pada hari libur dapat berubah diam-diam. Sebaiknya pertahankan data valid terakhir dan tampilkan kegagalan sinkronisasi.

## Interpretasi tiga tes bawaan yang gagal

1. Schedule clear: mismatch site dipaksa ke site sendiri lalu redirect 302; tes mengharapkan 403. Perlu keputusan perilaku, dengan penolakan eksplisit lebih aman.
2. Primary pages: `/report` sekarang redirect ke site, sedangkan tes menuntut 200. Ini ekspektasi tes yang perlu disesuaikan; kegagalan awal juga membuat URL berikutnya dalam loop tidak diperiksa.
3. Report export: 404 akibat benturan route; bug aplikasi terkonfirmasi.

## Yang sudah baik

Tes mengonfirmasi autentikasi/logout, idle timeout, CSRF recovery, larangan eskalasi role, kontrol akses beberapa operasi daily report, validasi kuota cuti dan pencegahan approval dua kali, pencegahan transfer stok diproses dua kali, serta pembatasan jadwal/absensi setelah resign. Approval transfer memakai transaksi dan row lock; schema stok memiliki unique key per sparepart/site/condition.

## Urutan perbaikan

1. Tutup jalur fast approve lintas site, edit setelah approval, mutasi master site dan jadwal; batasi field API absensi.
2. Perbaiki cleanup payroll historis dan side effect penghapusan lampiran bulk.
3. Perbaiki routing/relasi laporan dan parsing nominal import.
4. Pindahkan tes reproduksi menjadi regression test, tambah matriks role/site/status, dan perbaiki smoke test agar setiap halaman tetap diuji meski halaman lain gagal.
5. Verifikasi integrasi pada MySQL, browser dan PDF; lanjutkan pengujian beban/backup serta audit dependency.

Dokumentasi README juga perlu diperbarui: role dan cakupan fitur belum sesuai HR/payroll/reimbursement, contoh konfigurasi database kosong, dan tidak ada workflow CI yang ditemukan dalam pemeriksaan ini.
